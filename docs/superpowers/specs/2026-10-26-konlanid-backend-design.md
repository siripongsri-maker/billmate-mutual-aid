# คนละนิด — ระบบหลังบ้าน: ลงทะเบียนผู้ขอ, สลิป, ใบเสร็จ และหน้าแอดมิน

วันที่: 26 ต.ค. 2569 · สถานะ: รอเจ้าของโปรเจกต์ตรวจ

## 1. เป้าหมาย

คนละนิดให้คนในชุมชนช่วยกันจ่ายบิลจำเป็นของกันและกัน คนละนิด (เริ่ม ฿20) โดย**เงินโอนเข้าพร้อมเพย์ของผู้ขอโดยตรง** ระบบต้องทำให้คนช่วยไว้ใจได้ว่า (1) ผู้ขอเป็นตัวจริง (2) บิลเป็นของจริงและเป็นรอบปัจจุบัน (3) ยอดที่แสดงตรงกับเงินที่เข้า และ (4) เงินถูกนำไปจ่ายบิลจริง

**สำเร็จเมื่อ**
- ผู้ขอสมัคร ยืนยันตัวตน ยื่นบิล และเห็นบิลขึ้นหน้าเว็บได้เอง หลังทีมตรวจผ่าน
- คนช่วยโอนผ่าน QR พร้อมเพย์ อัปโหลดสลิป และเห็นยอดขึ้นแบบ "รอยืนยัน" ทันที โดยไม่ต้องสมัคร
- ผู้ขอยืนยันรับเงินแต่ละสลิป ยอดบนหน้าเว็บขึ้นเป็น "ยืนยันแล้ว"
- ครบยอดแล้ว ผู้ขอส่งใบเสร็จภายใน 7 วัน ทีมตรวจแล้วบิลขึ้น "จ่ายบิลแล้ว"
- ทีมเห็นงานค้างทั้งหมดในหน้าภาพรวม และจัดการได้จากหน้าแอดมิน
- ไม่ต้องแก้ `data.js` ด้วยมืออีก

## 2. การตัดสินใจที่ตกลงแล้ว

| เรื่อง | ตัดสินใจ |
|---|---|
| เงินไปที่ไหน | พร้อมเพย์ของผู้ขอ (QR ใส่ยอด, ทุกธนาคาร) |
| ลำดับการทำ | ทำครบ 3 ส่วน (ลงทะเบียน+ตรวจ, สลิป+ยอด, แอดมิน) ก่อนเปิดใช้จริง |
| ผู้ขอล็อกอิน | LINE, อีเมล, Google |
| คนช่วย | ไม่ต้องสมัคร, ฝากข้อความถึงผู้ขอได้ (ไม่บังคับ) |
| ตรวจตัวตน | บัตรประชาชน + เซลฟีถือบัตร + รูปบิล; ชื่อบัตร = ชื่อบิล = ชื่อบัญชีพร้อมเพย์ |
| ThaID | ยังไม่ใช้ตอนเปิด; ออกแบบให้เพิ่มเป็นทางเลือกแทนบัตร+เซลฟีภายหลัง |
| สลิป | ขึ้นยอดทันทีแบบ "รอยืนยัน"; ระบบกันสลิปซ้ำด้วยการอ่าน QR บนสลิป |
| ใครยืนยันเงินเข้า | ผู้ขอกดยืนยันเอง ทีมดูแลกรณีมีปัญหา |
| หลักฐานจ่ายบิล | ผู้ขอต้องส่งใบเสร็จภายใน 7 วันหลังครบยอด |
| เกณฑ์บิล | บิลรอบล่าสุดในชื่อผู้ขอ ค้างไม่เกิน 1 เดือน (เกิน 30 วันปิดรับอัตโนมัติ) |
| สถาปัตยกรรม | แนวทาง A: ย้ายคนละนิดเข้าแอป React (TanStack Start) + Lovable Cloud |

## 3. สถาปัตยกรรม

- **แอป:** สร้างหน้าคนละนิดใหม่เป็น route ใน `src/routes/` ของแอป TanStack Start เดิม ใช้ดีไซน์ โทเคนสี ฟอนต์ และภาพวาดจาก `public/konlanid/` (ย้ายโทเคนเข้า `src/styles.css`)
- **ลบแอปตัวอย่าง "ช่วยกัน" เดิม** (route `browse`, `bills.$id`, `circles`, `corporate`, `impact`, `moderator` ฯลฯ และ `src/lib/data.ts`, `store.tsx`) หลังหน้าใหม่พร้อม
- **`public/konlanid/` (หน้าเว็บนิ่งปัจจุบัน)** ใช้ต่อจนหน้าใหม่พร้อม แล้วให้ `/` และ `/konlanid/*` redirect ไปหน้าใหม่
- **หลังบ้าน:** Lovable Cloud (Supabase) — Postgres + Auth + Storage
  - งานที่ต้องใช้สิทธิ์สูง (อนุมัติ, เปลี่ยนสถานะ, สร้างลิงก์ดูเอกสาร) ทำใน **server function** ของ TanStack Start ด้วย service role ที่ฝั่ง server เท่านั้น
  - งานของผู้ใช้ทั่วไปใช้ client ที่มี RLS
- **การเปลี่ยนฐานข้อมูล:** Lovable เก็บ migration ไว้ที่ `drizzle/migrations/` (มี journal และ snapshot) — เขียน SQL ให้รันซ้ำได้ แล้วให้ Lovable เป็นคนสร้าง migration ในระบบของมันและยืนยันผลด้วยคำสั่งตรวจ (แบบเดียวกับ `contact_messages`); ไม่เพิ่มไฟล์ใน `supabase/migrations/` อีก

## 4. ข้อมูล

ตารางทั้งหมดอยู่ใน `public`, เปิด RLS ทุกตาราง

| ตาราง | คอลัมน์หลัก | หมายเหตุ |
|---|---|---|
| `profiles` | `user_id` (FK auth.users), `display_name`, `contact`, `role` (`requester`/`admin`/`owner`), `suspended_until`, `created_at` | 1 แถวต่อผู้ใช้ สร้างอัตโนมัติตอนสมัคร |
| `verifications` | `id`, `user_id`, `legal_name`, `id_card_path`, `selfie_path`, `status` (`pending`/`approved`/`rejected`/`needs_more`), `reason`, `reviewed_by`, `reviewed_at`, `method` (`id_selfie`/`thaid`) | `method` เผื่อ ThaID |
| `bills` | `id`, `requester_id`, `type`, `label`, `title`, `story`, `region`, `display_alias`, `goal`, `due_date`, `bill_image_path`, `promptpay_id`, `promptpay_name`, `name_check` (ผลทีมสแกนดูชื่อบัญชี), `status`, `confirmed_total`, `pending_total`, `helpers_count`, `funded_at`, `receipt_path`, `receipt_due_at`, `paid_at`, `reject_reason`, `created_at` | ยอดรวมคำนวณด้วย trigger จาก `contributions` |
| `contributions` | `id`, `bill_id`, `amount`, `slip_path`, `slip_ref_hash` (unique), `slip_payload`, `message`, `helper_alias`, `helper_token_hash`, `status` (`pending`/`received`/`not_received`/`invalid`), `confirmed_at`, `created_at` | `helper_token` เก็บในเครื่องคนช่วย ใช้ดูสถานะของตัวเองโดยไม่ต้องสมัคร |
| (รายงาน) | ใช้ `contact_messages` ที่มีอยู่ (topic `report`, มี `bill_id`) | ไม่สร้างตารางใหม่ |
| `audit_log` | `id`, `actor_id`, `action`, `target_type`, `target_id`, `detail` (jsonb), `created_at` | เขียนจาก server function เท่านั้น, ห้ามแก้/ลบ |
| `settings` | `key`, `value` | `overdue_limit_days`=30, `receipt_days`=7, `doc_retention_days`=30, `pending_alert_hours`=48 |

**สถานะบิล:** `draft` → `submitted` (รอตรวจ) → `open` (เปิดรับ) → `funded` (ครบยอด, รอใบเสร็จ) → `receipt_submitted` → `paid` · ทางแยก: `rejected`, `paused` (ทีมพักระหว่างตรวจรายงาน), `closed` (ถอนเอง/ค้างเกิน 1 เดือน), `receipt_overdue`

**กติกาในฐานข้อมูล**
- ผู้ขอมีบิลสถานะ `submitted`/`open`/`funded`/`receipt_submitted` ได้ทีละ 1 บิล
- ยื่นบิลได้เมื่อ `verifications.status = approved` และไม่มีบิล `receipt_overdue`
- `open` → `funded` อัตโนมัติเมื่อ `confirmed_total >= goal` (ใช้ยอดยืนยันแล้วเท่านั้น); รับสลิปใหม่ไม่ได้เมื่อ `confirmed_total + pending_total >= goal` (ถ้าสลิปที่รอถูกตัดสินว่า `not_received`/`invalid` บิลกลับมารับได้อีก)
- เกิน `due_date + 30 วัน` → `closed` (งานตั้งเวลาวันละครั้ง)

**ที่เก็บไฟล์ (private bucket):** `id-docs` (บัตร, เซลฟี), `bills`, `slips`, `receipts` — ไม่มี bucket สาธารณะ เปิดดูด้วย signed URL อายุ 5 นาทีเท่านั้น

## 5. ขั้นตอนการใช้งาน

### ผู้ขอ
1. ล็อกอินด้วย LINE / อีเมล / Google → สร้าง `profiles` (ตั้งชื่อเรียกเอง)
2. ยืนยันตัวตน: กรอกชื่อตามบัตร, ถ่าย/อัปโหลดบัตร + เซลฟีถือบัตร, ยินยอมตามข้อความ PDPA → `verifications.pending`
3. ทีมตรวจผ่าน → ยื่นบิล: ประเภท, รูปบิล, ยอด, วันครบกำหนด, พร้อมเพย์ (แนะนำเบอร์มือถือ), ชื่อเรียก, จังหวัด, เรื่องราว, ยินยอมเรื่องข้อมูลที่แสดง (รวมถึง "แอปธนาคารจะแสดงชื่อบัญชีพร้อมเพย์") → `submitted`
4. ทีมตรวจบิล + สแกน QR ดูชื่อบัญชี → `open`
5. เห็นสลิปที่เข้ามา → กด **ได้รับแล้ว** / **ยังไม่เข้า** (ดูรูปสลิปได้เพื่อเทียบ)
6. ครบยอด → อัปโหลดใบเสร็จภายใน 7 วัน → ทีมตรวจ → `paid`

### คนช่วย (ไม่ต้องสมัคร)
1. เลือกบิล → เลือกยอด (฿20 ขึ้นไป ไม่เกินยอดที่ยังขาด)
2. QR พร้อมเพย์ใส่ยอด → บันทึก/สแกนในแอปธนาคาร → ตรวจชื่อบัญชีตรงกับที่หน้าเว็บแสดง
3. อัปโหลดสลิป + ข้อความถึงผู้ขอ (ไม่บังคับ) + ชื่อเรียก (ไม่บังคับ)
   - เบราว์เซอร์อ่าน QR บนสลิปด้วย `jsQR` → ส่ง payload ไป server → server ทำ hash เก็บใน `slip_ref_hash` (unique) — สลิปซ้ำถูกปฏิเสธทันที
   - สลิปที่ไม่มี QR ยังส่งได้ แต่ติดป้าย "ตรวจด้วยตา" ให้ผู้ขอ/ทีม
   - ยอดในสลิปที่อ่านได้ต้องตรงกับยอดที่เลือก; ไม่ตรงให้แก้ก่อนส่ง
4. เห็นสถานะของตัวเองในหน้า "รวมกันคนละนิด" ผ่าน `helper_token` ที่เก็บในเครื่อง

### ทีม (แอดมิน) — ตามส่วนที่ 2 ที่ผ่านแล้ว
- **ภาพรวม:** ตัวเลขงานค้าง (ตัวตนรอตรวจ, บิลรอตรวจ, สลิป `not_received`, สลิป `pending` เกิน 48 ชม., ใบเสร็จรอตรวจ, ใบเสร็จเกินกำหนด, บิลใกล้ค้างเกิน 1 เดือน, ข้อความใหม่) + ภาพรวม (บิลเปิดรับ, ยอดยืนยันแล้ว/รอยืนยัน, แรงช่วยสัปดาห์นี้)
- **ตรวจตัวตน / ตรวจบิล / สลิปมีปัญหา / ใบเสร็จ / ข้อความ / ผู้ใช้ / บันทึก / ตั้งค่า**
- ตัดสินทีละรายการ ไม่มีอนุมัติหลายรายการพร้อมกันสำหรับตัวตนและบิล; ปฏิเสธต้องเลือกเหตุผล
- ตารางเปลี่ยนเป็นการ์ดบนมือถือ, สถานะมีข้อความกำกับเสมอ

## 6. ความปลอดภัยและความเป็นส่วนตัว

**สิทธิ์ (RLS)**
- สาธารณะ: อ่านได้เฉพาะ view `public_bills` (สถานะ `open`/`funded`/`receipt_submitted`/`paid`; คอลัมน์ `display_alias`, `region`, `type`, `title`, `story`, ยอด, สถานะ, `due_date`) และข้อความของคนช่วยที่ผ่านแล้ว — **ไม่เปิด** `promptpay_id`/`promptpay_name` ใน view; หน้า pay ขอ QR จาก server function ที่คืนเฉพาะ payload QR + ชื่อบัญชีแบบย่อ
- ผู้ขอ: อ่าน/แก้ `profiles` ของตัวเอง, อ่าน `verifications` และ `bills` ของตัวเอง, อ่าน `contributions` ของบิลตัวเอง, อัปเดตได้เฉพาะ `status` ของสลิปเป็น `received`/`not_received` ผ่าน server function
- คนช่วย: สร้าง `contributions` ผ่าน server function เท่านั้น (ตรวจยอด, สลิปซ้ำ, rate limit ต่อ IP)
- แอดมิน: ทุกอย่างผ่าน server function ที่เช็ก `role` และเขียน `audit_log` ทุกครั้ง
- เฉพาะบทบาท `owner` (เจ้าของระบบ) ที่เพิ่ม/ลบแอดมินได้

**เอกสาร**
- signed URL 5 นาที, ลายน้ำ "สำหรับตรวจเท่านั้น" บนภาพที่แสดงในหน้าแอดมิน, ไม่มีปุ่มดาวน์โหลด, บันทึกการเปิดดูใน `audit_log`
- **ลบอัตโนมัติ:** บัตร+เซลฟี 30 วันหลังบิลล่าสุดของผู้ขอปิด (`paid`/`closed`/`rejected`) หรือ 30 วันหลังตรวจตัวตนไม่ผ่าน; รูปบิล+สลิป+ใบเสร็จเก็บ 180 วันหลังปิดบิล (เป็นหลักฐานกรณีร้องเรียน) แล้วลบ — ตัวเลขปรับได้ใน `settings`
- ผู้ขอขอลบบัญชีได้จาก `/me` (ลบเอกสารทันที เก็บเฉพาะบันทึกยอดที่จำเป็น)

**ข้อความที่ต้องบอกผู้ใช้ตรง ๆ**
- ตอนคนช่วยโอน แอปธนาคารจะแสดงชื่อบัญชีพร้อมเพย์ของผู้ขอ และ QR มีเลขพร้อมเพย์อยู่ข้างใน
- ทีมเห็นเอกสารเท่าที่จำเป็นต่อการตรวจ
- ไม่มีระบบสาธารณะตรวจบัญชีม้า; ทีมตรวจด้วยการเทียบชื่อ 3 จุดและเซลฟี

**กันการใช้ผิด:** rate limit การส่งสลิป/ข้อความต่อ IP, honeypot ในฟอร์มสาธารณะ, ผู้ขอทีละ 1 บิล, พักสิทธิ์เมื่อใบเสร็จเกินกำหนด, รายงานจากสาธารณะพักบิลได้ (ทีมตัดสิน)

## 7. การจัดการข้อผิดพลาด

- อัปโหลดล้มเหลว: เก็บข้อมูลในฟอร์มไว้, ให้ลองใหม่, ไม่สร้างแถวครึ่ง ๆ (อัปโหลดไฟล์ก่อน แล้วค่อยสร้างแถวใน server function เดียว; ไฟล์กำพร้าลบด้วยงานตั้งเวลา)
- สลิปซ้ำ: ข้อความ "สลิปนี้เคยส่งแล้ว" ไม่บอกว่าเป็นของบิลไหน
- บิลปิดระหว่างที่คนช่วยกำลังโอน: หน้า pay เช็กสถานะอีกครั้งก่อนรับสลิป; ถ้าปิดแล้วแจ้งให้ติดต่อผู้ขอผ่านทีมเพื่อคืนเงิน
- ผู้ขอกด "ยังไม่เข้า": สลิปไปคิว "สลิปมีปัญหา" ทีมติดต่อทั้งสองฝ่าย (ถ้าคนช่วยให้ช่องทางไว้)

## 8. การทดสอบ

- **RLS:** สคริปต์ทดสอบด้วย key สาธารณะ + ผู้ใช้ทดสอบ 3 บทบาท ว่าอ่าน/แก้/ลบได้เฉพาะที่ควร (แบบเดียวกับที่ทดสอบ `contact_messages`)
- **ตรรกะยอด:** unit test ของ trigger/ฟังก์ชัน: pending→received, ครบยอด→funded, เกินยอดถูกปฏิเสธ, สลิปซ้ำถูกปฏิเสธ
- **QR:** test ของ `promptPayPayload` (CRC, เบอร์/เลขบัตร/e-wallet) และการอ่าน payload สลิปจากภาพตัวอย่าง (ภาพสลิปปลอมที่สร้างเอง ไม่ใช้สลิปจริง)
- **E2E:** ผู้ขอสมัคร→ตรวจ→ยื่นบิล→ทีมอนุมัติ→คนช่วยโอน+สลิป→ผู้ขอยืนยัน→ครบยอด→ใบเสร็จ→paid บนมือถือ 390px และเดสก์ท็อป
- **ทดสอบจริงก่อนเปิด:** โอนจริง ฿20 จากอย่างน้อย 3 ธนาคาร (กสิกร, SCB, กรุงเทพ) เข้าพร้อมเพย์ทดสอบของทีม

## 9. ความเสี่ยงและเรื่องที่ต้องยืนยัน

- **LINE Login:** Lovable Cloud ไม่มี LINE ในตัว → ทำ OAuth กับ LINE ใน server function, ตรวจ `id_token`, แล้วสร้าง session ผ่าน Supabase admin API; ต้องสร้าง LINE Login channel (ฟรี) และตั้ง callback URL — ถ้าติดปัญหา เปิดด้วยอีเมล+Google ก่อน แล้วเพิ่ม LINE ทีหลัง
- **รูปแบบ QR บนสลิปแต่ละธนาคาร:** ต้องเก็บตัวอย่างจริงเพื่อยืนยันว่าอ่านได้และ payload ไม่ซ้ำกันข้ามรายการ
- **กฎหมาย:** การชวนประชาชนร่วมให้เงิน อาจเกี่ยวกับกฎหมายการเรี่ยไร และ PDPA (ต้องมีประกาศความเป็นส่วนตัวและผู้รับผิดชอบข้อมูล) — ควรให้ฝ่ายกฎหมาย/ผู้บริหารองค์กรตรวจก่อนเปิดสาธารณะ
- **ภาระทีม:** ทุกบิลต้องตรวจด้วยคน; ถ้าคำขอมากต้องมีคนตรวจพอ

## 10. ไม่ทำในรอบนี้

ThaID, ระบบตรวจสลิปอัตโนมัติกับธนาคาร (บริการเสียเงิน), แจ้งเตือนทีมผ่าน LINE, กราฟวิเคราะห์, หลายภาษา (ใช้ภาษาไทยก่อน), แอปมือถือ

## 11. ลำดับการสร้าง (ร่าง สำหรับแผนลงมือ)

1. ฐานข้อมูล + RLS + storage + server function พื้นฐาน + ระบบ role
2. ล็อกอิน (อีเมล, Google, แล้ว LINE)
3. หน้าแอดมิน: ภาพรวม, ข้อความ, ตรวจตัวตน, ตรวจบิล
4. ผู้ขอ: ยืนยันตัวตน, ยื่นบิล, หน้าบิลของฉัน
5. หน้าสาธารณะใหม่ใน React (ย้ายดีไซน์จาก `public/konlanid`) + QR พร้อมเพย์ + อัปโหลดสลิป
6. ผู้ขอยืนยันสลิป, ใบเสร็จ, งานตั้งเวลา (ปิดบิลค้าง, ใบเสร็จเกินกำหนด, ลบเอกสาร)
7. ทดสอบ RLS/E2E, ทดสอบโอนจริง, ลบแอปตัวอย่าง "ช่วยกัน", redirect หน้าเก่า
